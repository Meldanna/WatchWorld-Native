## 心得

1. **「上游失败」与「装配失败」是两条路，落点不该相同。**
   `runToolChat` 除取消外**不抛**：它把失败原因写成正文里的一条 note（`[请求失败：{上游原文}]`）。
   于是 `ChatViewModel` 的 `catch` 只接得住「自己装配时炸的」（没 Provider、没 Agent）。
   第一版我把两者都塞进 `state.error`，测试直接顶回来：上游 500 时 `state.error` 是 `null`。
   想清楚之后反过来更有道理 —— 失败原因必须落在**那条消息**上（用户能对着它继续对话），
   顶栏再重复一遍纯属噪音。现在两条路径各有专门用例钉住。
2. **取消分支里的落库必须包 `NonCancellable`。**
   用户按停止时协程已被取消，`sessionRepository.save()` 里第一个挂起点就会再抛一次
   `CancellationException`，部分正文与 `[已停止生成]` 一条都存不下来。
   这正是 T09 gotcha「取消路径里补一句提示，反而又抛一次」的同一条纪律，只是这次踩在**数据库写**上。
   `stoppingKeepsPartialTextAndMarksTheMessageStopped` 守住。
3. **标题截断的期望值我按直觉写错了。**
   先在用例里手写「这是一条很长的第一条用户消息用来验证标题截」，跑挂了才发现少了省略号；
   对照 `App.tsx` 的 `text.slice(0, 20) + (text.length > 20 ? '...' : '')` 才对齐。
   **移植 JS 字符串逻辑时先手推 JS 语义再写断言**（gotchas 里已有同类记录，又踩一次）。
4. **离屏像素测试要挑「只有一种实现能通过」的样本。**
   最初的反证写的是「顶层 `content` 有字、`versions` 为空 → 不该有字」，这条期望本身就是错的：
   TS 的 `(versions[i] || versions[0])?.content || m.content` **本来就会**兜底到顶层。
   改成「`versions[0]` 空、正文在 `versions[1]`、`currentVersionIndex = 1`」之后判别力才成立
   —— 只读 `versions.first()` 或只读顶层都会渲染成空白。兜底行为另立一条用例正面断言。
5. **`ChatViewModel` 不持有原始数据，只信 Repository 的返回值。**
   `SessionRepository` 每个写方法都返回「盖好 `updatedAt` 的权威副本」，
   ViewModel 用它更新内存状态并回调 `SessionViewModel.replace`；两边各持一份状态但不各自造数据，
   侧边栏、聊天区、数据库三者不会互相漂移。

## 要点

- **正文存放按角色不对称**（legacy fixture 实测）：assistant 正文在 `versions[currentVersionIndex]`，
  user 正文在顶层 `content` 且 `versions` 是空数组。取值顺序必须是
  `versions[idx] → versions[0] → content`（`api.ts:328` 的 `||` 语义），
  `MessageBubble` / `ChatScreen` / `ChatViewModel` 三处一致。**别写 `versions.first()` 就完事**。
- **采样参数回退链**（`ChatRequestAssembler`，照抄 `api.ts` 原生分支）：
  `temperature = session ?? defaults ?? agent ?? 0.7`、`topP = session ?? defaults ?? agent ?? 0.95`、
  `topK / frequencyPenalty / presencePenalty / maxTokens = session ?? defaults`、
  `toolCallStepLimit = session ?? defaults ?? 0`、`stream = session.streamingEnabled != false`。
  `null` 是「不传这个键」，**不许**用默认值把它填上（`ChatRequestAssemblerTest` 三条用例钉死）。
- **上游失败 vs 装配失败**：前者进正文（工具循环的 note），后者进 `state.error`。
  两条路径都有专门用例；改 `ChatViewModel` 的 catch 结构前先跑 `ChatViewModelTest`。
- **取消路径的写操作一律 `withContext(NonCancellable)`**，否则部分正文存不下来。
- **`DefaultData.kt` 的两个常量同时影响两件事**：全新安装的默认设置，以及
  `ArchiveStore.snapshot()` 对老存档缺字段时的补齐。改值必须同步改
  `StorageRoundTripTest.withStorageDefaults`，否则 T07 往返测试会假失败。
- **UI 只拿 Repository**：两个 ViewModel 的构造参数全是 `SessionRepository` / `SettingsRepository` /
  `ConfigRepository`，`ui/` 下没有任何 `*Dao` 引用。
- **启动行为**：`App()` 里 `load()` 后若库里没有会话就建一个再 `load()` —— 否则界面永远停在空态。
  偏好里的 `launchMode`（`last` / `new`）要等 T15 的设置界面才有地方配。
- **`ensureAppDataDir()` 是新的 expect 顶层函数**：KMP 版 Room 把 `name` 当**路径**用，
  目录不存在会直接报错，所以开库前必须先建目录。T22 加 Android 目标时要补 actual。
- **T04 的 Gemini 在线生成不再是阻塞条件**：用户账号只能拉模型列表，免费版无法通过 API 取回复。
  Gemini 协议分支由 `SseProviderAdapterTest` 的协议级样例覆盖；T14 链路测试用 OpenAI 兼容假上游
  （与生产同一条 `preparePost().execute{}` + 逐行读路径，不是 mock 客户端）。
- **本任务编号是 T14**，文档路径 `tasks/T14-会话与侧边栏.md`（与 WORKPLAN §二 索引一致）。
  T13 是 Markdown 流式渲染，两者不要混。
