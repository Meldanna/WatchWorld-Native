## 心得

- **Markdown 库决策 #2 仍未拍板，所以本任务自建极简渲染器**（用户当场确认走这条）。
  这样做的关键好处是把「切块 + 缓存」与「单块怎么渲染」**解耦**了：
  T13 换成 `compose-markdown` 时只改 `MarkdownBlock` 的正文解析，`splitBlocks` 与缓存策略一行不用动。
  如果反过来先引库再想缓存，两件事会缠在一起。
- **块级缓存在 Compose 里不需要手写缓存表**。`remember(block)` + `key(index, block)` 就够：
  非末块的字符串不变 → `remember` 命中 → 不重解析；末块每帧变 → 只有它重解析。
  PLAN §7.3 那段伪代码用的是 `LazyColumn`，这里改成普通 `Column` —— 因为消息正文嵌在
  **消息列表的 LazyColumn 里**，内层再套 `LazyColumn` 会变成嵌套滚动，是坑不是特性。
- **光标闪烁要用 `SpanStyle(color = accent.copy(alpha = …))` 而不是改透明度 modifier**：
  光标是**行内**字符，得跟着编辑文字排版走；用 modifier 单独放一个 View 会飘在行外。
- **「停止」的收尾必须写在 `finally`**：`streamJob.cancel()` 会让 `collect` 抛 `CancellationException`，
  如果只在正常路径把 `streaming = false`，取消后按钮会永远卡在「停止」态。
- **T02 不引 ViewModel**：`lifecycle-viewmodel-compose` 是额外依赖，而 T02 只证明链路。
  用 `remember` + `rememberCoroutineScope` 即可；T14 拆 `ChatViewModel` 时整体搬走（PLAN §7.4 已规划）。
- **⚠️ 踩到一个工具坑**：会话项目根是打开客户端时所在的仓，**不等于 `FILE_LAYOUT.md` 认定的工作区**，
  导致第一轮 `write_file` 把文件写到了 C 盘另一个仓，构建却报 `UP-TO-DATE`（假成功）。详见 `memory/gotchas.md`。

## 要点

- **`MockChatStream` 是临时脚手架**，不在 `FILE_LAYOUT.md` §3 的正式目录里。**T03 落地真实客户端后删除它。**
- **`FRAME_INTERVAL_MS = 50` 是人为设定值**，**不构成** PLAN §8.2「真流式验收」的判据；
  真流式要看 T03 的 Ktor 客户端帧间隔是否贴近上游节奏（基线 `311, 310, 313, 309, 310, 311, 314` ms）。
- **T13 换库的替换点集中在**：`MarkdownBlock`（正文解析）、`inlineAnnotated`（行内语法）、`stripFence`（围栏剥离）。
  `splitBlocks` 的切块语义（围栏内空行不切）与 `StreamingMarkdown` 的缓存策略**换库后必须保留**。
- **`UiMessage` 是临时模型**：T05 会用 §4 迁移出的真实 `ChatMessage`（19 字段）**整体替换**，不是扩展它。
  别往 `UiMessage` 上加贴近存档的字段。
- **`App()` 仍是双端唯一入口**：T02 起它挂 `ChatScreen`；桌面 `Main.kt` 依然只做「开窗口 + 调 `App()`」。
- **`ChatScreen` 的状态（messages / streaming / job）是 T14 迁移的起点**，拆分时整体搬进 `ChatViewModel`。
- 边界已处理（PLAN §7.3）：
  - 未闭合围栏代码块 → `stripFence` 仍按代码块渲染，内容不丢；
  - 未闭合行内标记（`**bo`）→ `inlineAnnotated` **原样输出**，不吞字；
  - 空内容 → `splitBlocks` 返回 `[""]`，保证光标有落点。
