## 目标与可见效果

- **目标**：把 Web 版的 IndexedDB 图片存储迁移到原生文件系统 —— 对应的 `imageStore.ts` 的 `ImageStore` 类迁移到 Kotlin。
- **可见效果**：
  1. 聊天消息中带图片的气泡能正常显示图片占位；
  2. 图片保存到 `%APPDATA%\WatchWorld\images\`（Windows 桌面端）；
  3. `ImageStore.saveFile(bytes, mime, name)` 接收图片字节，返回 `StoredImage`（含 dataUrl）；
  4. `ImageStore.get(id)` / `getMany(ids)` 按 id 读取图片；
  5. `ImageStore.pruneOrphans(usedIds)` 清理未被引用的图片；
  6. `ImageStore.usage()` 返回图片数量与总字节数，供设置界面显示。

## 心得

- **数据格式选 dataURL 而非二进制文件**：Web 版的 `StoredImage` 本来就只有 dataUrl，落盘的就是整个 JSON，好处是 WebDAV 的 `pushImageFile` 一 JSON 直接就是 payload，不用二次转换。
- **图片压缩规则要精确 replicate**：Web 版的 `compressImageFile` 有两条硬性规则：
  1. 原图 ≤ 400KB 且最长边 ≤ 1600 → 原样保留（不二次编码）；
  2. 否则等比缩放：PNG 保持 PNG（可能带透明通道），其余转 JPEG 并使用 0.85 的 quality 参数。
- **IO 操作必须切线程池**：一次 dataURL 写入可能是几 MB，不能让它在 Compose 的主线程上跑，使用 `Dispatchers.IO`。
- **`ImageStore` 设计为普通类而非 expect/actual class**：Kotlin 2.4 的 expect class 仍是 Beta，会产生编译警告；改用 `expect fun defaultImageBlobStore(): ImageBlobStore` 返回注入的实现更干净。
- **temp 文件写完再改名**：写入时先写临时文件再 `renameTo`，中途崩溃/断电时不会留下半截 JSON 被当成有效图片。

## 要点

- `StoredImage` 字段名**逐字**照抄 Web 版（`id`/`dataUrl`/`mime`/`width`/`height`/`bytes`/`name`/`createdAt`），WebDAV 云端互认；
- 图片本体不进 Room、不进 v5 存档，只有 id 引用（`ChatMessage.imageIds`）；
- `compressImageBytes` 读取失败时不抛，退回原图（有损总好过丢图）；
- **文件布局**：`%APPDATA%\WatchWorld\images\<id>.json`，一图一文件，不建子目录、不改文件名；
- `ImageStore.saveFile` 内部调用 `compressImageBytes` 再 `put`，返回完整的 `StoredImage`；
- **Android 平台归 T22**：桌面端实现满足 P0–P4 阶段需求，Android 用 `Context.getFilesDir()`，但那是 T22 的事。
