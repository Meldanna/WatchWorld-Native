## 心得

### 1. Tailwind v4 的 oklch 值与 v3 hex 不是同一套颜色(测试向量前提整个错了)

最初设计验收向量:「7 个预设的 primaryHex 必须等于色阶 600 档解回来的 sRGB」——全部对不上
(emerald 差 5/3/3,violet 差 4/24/17)。手算 + 逐值排查后确认:**Tailwind v4 的 oklch 表是重新调的**,
同名档与 v3 时代 hex 同名不同色(emerald-600 v4 表 `oklch(59.6% 0.145 163.225)` 按 CSS Color 4
解回 **#009966**,v3 表是 #059669;L/h 一致,只有色度 C 不同)。React 仓 theme.ts 两者混用:
色阶用 v4 oklch(浏览器实际渲染的色),primaryHex 用 v3 hex(仅列表圆点)。
**结论:浏览器才是 ground truth,Compose 必须同样按 oklch 解色才能与 Web 观感一致。**
向量测试改为「v4 oklch → 期望 = 浏览器渲染值」(DevTools 可复核),正向用 hex→oklch 手算参考值守住矩阵。
这条也解释了为什么"往返 ±1"测试通过而向量全挂——往返只验证自洽,与 v4 表不可往返无关。

### 2. theme.ts 同一模板串里混用两种数字精度(L 是 toString,C/H 是 toFixed)

`buildScale` 输出对快照总差一位:L 多尾零(`95.0000` vs `95`)、C 又少尾零(`0.068` vs `0.0680`)。
反复猜了五轮规则,最后用 Node 直接实证 JS 语义才定案:模板 `` `oklch(${L}% ${c.toFixed(4)} ${h.toFixed(2)})` ``
里 **L 是 number 隐式 toString(去尾零)**,只有 C/H 走 `toFixed`(固定小数位、**保留**尾零;
node 实测 `(0.068).toFixed(4)==="0.0680"`、`(95).toFixed(4)==="95.0000"`)——
"toFixed 去尾零"是和 `toString` 记混的错记忆。family m2 直乘路径的 L/h 则是字符串原样透传。
**方法教训:凭直觉猜 JS 格式化行为必错,一个 node -e 就能裁决;快照对拍是最终裁判。**
最终 Kotlin 拆成 `toCssNumber`(toString 语义)与 `toFixedCss4/2`(toFixed 语义)两个助手,
快照 15 套全等。

### 3. 角色层是「两维解引用」,不能编译期算死

角色串如 `text-m1-500 dark:text-m1-400` 在**主题变体**(STANDARD/MIDNIGHT)与 **uiMode**
两个维度上取不同档,且 `bg-m1-500/15` 要把 alpha 折进颜色。设计为:字符串 1:1 保存
(`ThemeRoles`),解析时按首 light 片段 / 首 dark 片段各取一档,解引用需要当前主题色阶 ——
用 `roleCurrentVars` 全局上下文承载(Compose 组合主线程串行,窗口不会被打破;T22 引入多线程再改显式传参)。
`hover:` 只改交互态不变色,`shadow-sm`/裸 `border` 等非颜色片段跳过。

### 4. 双轨方案(用户拍板)

①由主题生成 Material3 `ColorScheme` 喂 `MaterialTheme`——现有 `OutlinedTextField`/`Button`/`Surface`
自动跟随主题,**一行不改就不再吃默认紫**;②新代码用 `WwTheme.colors`,字段语义与 Web 版类名一一对应。
主档位不硬编码主题 id:从 `primaryBg`/`primaryHover` 角色串解出档位(STANDARD=600/500,
MIDNIGHT=700/600),新增变体时无需改 Material 桥。

### 5. E2E 截图验证的两处坑

`CopyFromScreen` 截的是**前台**窗口:`SetForegroundWindow` 会被系统拦截(前台进程锁定),
第一张截到的是终端;换 `WScript.Shell.AppActivate` 才可靠前置。窗口标题精确匹配
`WatchWorld Native` 定位进程。验证脚本(`build/verify-theme.ps1` 等 3 个)会随 build 目录被清,
若要长期保留应移到 `fixtures/tools/`(收尾已移入)。

### 6. `oklch(… / A)` 的 alpha 要分「比例」和「百分数」(收尾补测抓到的真 bug)

CSS 的 `oklch(L% C H / A)` 里,**无单位 A 是 0..1 比例**(`/ 0.9` = 90% 不透明),带 `%` 才是百分数。
`CssColors.parse` 最初把抓到的 `0.9` 当百分数传给 `OklchColorMath.toSrgbInt(alphaPercent)`,于是
`--m1-bubble-dark = oklch(20.8% 0.042 265.755 / 0.9)` 被解析成 **0.9% 不透明**(alpha≈2/255)——
深色模式下 AI 气泡近乎全透明。**浅色 E2E 截图与「只比字符串」的快照对拍都抓不到**,是补 `CssColorsTest`
边界用例时发现的。修法:按有无 `%` 折算,alpha 边界用例守住;另加**无头离屏截图**用例
`DarkBubbleScreenshotTest` 从渲染侧再守一道(故意还原 bug 时会失败)。

## 要点

- **数字格式化契约**(改快照必挂,这是故意的):buildScale 中 L 走 `toCssNumber`(toString 去尾零),
  C 走 `toFixedCss4`、H 走 `toFixedCss2`(固定小数位保留尾零);family m2 的 L/h 是字符串透传,
  只有彩度 ×0.4 后走 `toFixedCss4`。JS 侧依据:node 实证 + 快照逐字。
- **v4 oklch ≠ v3 hex**:两者是不同颜色的表。任何「oklch 应该解回某个 hex」的直觉都要先问:
  这是哪张表的值?浏览器渲染值 = CSS Color 4 逆向 = 我们 `OklchColorMath.toSrgbInt` 的行为。
- **角色串解析规则**:首 light 片段定 light 档、首 `dark:` 片段定 dark 档;`hover:` 前缀剥掉不变色;
  `/NN` 折成 alpha;`shadow-sm`、裸 `border` 跳过。**不要**在编译期把角色串算成 Color。
- **App 根部必须 `WwTheme` 包裹**:`LocalWwColors` 无 provider 直接 error(fail-fast);
  `MaterialColorSchemeFactory` 依赖角色串可解析,角色串改了 Material 桥自动跟随。
- **`DesignTokens` 不随主题 id 变**(只随 uiMode,与 React 版一致);随主题变的只有 m1/m2/气泡/角色色。
- **字号 token 比例是 CSS calc 的算术值**,不是凑整:`15×0.9333=13.9995`、`15×1.3333=19.9995`
  (浏览器同样得这个数);弹窗小字(`text-[10px]` 等)与角标徽章**不走**这套。
- **快照 fixture 是权威**:`fixtures/theme-baseline/snapshots.json`(15 套 = 13 内置 + 2 custom 样本);
  custom 样本不在内置表里,对拍时按同 HEX `customThemeToConfig` 还原(走 `resolveTheme` 会假回退 emerald)。
- **`resolveTheme` 永不返回 null**:内置 → 自定义 → 回退 emerald;非法 hex 在 `resolveThemeVars`
  里回退 family 表(JS `?? FAMILY_SCALES.emerald` / `?? m1`)。
- **本机渲染后端**:skiko 默认 Direct3D 建窗即崩(`0xC0000409`),`desktopApp` 已默认 OPENGL,
  `-PwwRender=software` 兜底——E2E 截图验证依赖此前提。
- **color-mix / rgba 等其它 CSS 语法**:解析器**有意不猜**,返回 null 由调用方显式处理;
  目前主题数据里未出现这些写法。
