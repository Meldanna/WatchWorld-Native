## 心得

### 1. `detectTimelineIntent` 的正则远比「自然语言」窄 —— 必须拿 Node 实测，不能凭直觉写用例

第一版用例我随手写了「回到分支【A1】」「进入时间线：学园线」「这是一个新时间线」当**命中**样本，结果三条全挂。
拿 Node 跑原始 TS 正则才发现：**这些写法在 TS 里本来就不命中**。

- `switchPattern` 里 `(?:【|\[)?` 的位置在「时间线/分支」**之前**，所以「回到分支**【**A1**】**」这种「后缀方括号」写法匹配不上；
- 显式声明正则 `(?:一个|一条|一个全新的?)?` 只认「一个」「一条」「一个全新的」，**不认「一个新」**。

结论：**验收样本必须照 TS 正则实测生成**，否则会把「我的直觉」当成「TS 规格」。
临时用了 `scratch-t17.mjs` 脚手架（已删），出题前把每个候选串先喂给 Node。

### 2. 时间线树提示词从「调用方传字符串」改成「ContextBuilder 内部构建」

T08 时 `ContextBuilder` 只是把 `timelineContextPrompt` 当**透传参数**（因为 `buildTimelineTreePromptContext` 没迁）。
T17 迁完之后，如果继续让调用方算，那 ChatViewModel 的**四条生成路径**都要各自拼一遍，还得各自处理可见性短路 —— 直接把这段逻辑收进 `ContextBuilder` 第 6 步更不容易漏。
`timelineContextPrompt` 保留为**可选覆盖**：默认 `null` 走内部构建，显式给值才用（测试 `invisibleActiveTimelineSuppressesTimelinePrompt` 需要「强制塞一段」，未来窗口级定制也用得上）。

### 3. 描述标签解析里的「最多只接受一个申请」

TS 里是 `...(validProposals.length === 1 ? { proposal: validProposals[0] } : {})`。
一开始想「取 `validProposals.last()` 更宽容」，但那就是**擅自放宽协议**：模型被明确要求「附加一次且仅一次」，多打一段控制标记属于违规，应用应当**不采纳**。
Kotlin 用 `singleOrNull()` 精确表达这个语义，并有 `parseIgnoresMalformedInvalidAndDuplicateControls` 守着。

### 4. `JsonPrimitive` 会把数字读成字符串，`typeof value !== 'string'` 必须显式补

TS 的 `sanitizeText` 第一行是 `if (typeof value !== 'string') return undefined`。
Kotlin 第一版直接用 `(obj["x"] as? JsonPrimitive)?.content`，结果 `{"descriptionTag":123,...}` 被读成 `"123"` 并**通过**了校验 —— Kotlin 的 `JsonPrimitive.content` 对数字会返回字面量。
补 `.takeIf { it.isString }` 之后才对得上 TS。由 `parseRejectsEmptyAndNonStringFields` 守住。

### 5. `allocateTimelineCodeTag` 的根分支循环「看着像 bug，其实是规格」

```ts
for (let i = 0; i < letters.length; i++) {
  const letter = letters[i];   // ← 每个字母一进来
  let num = 1;                 // ← num 都重置为 1
  while (existingCodes.has(`${letter}${num}`)) num++;
  return `${letter}${num}`;    // ← 立即返回，永不进入下一个字母
}
```

初读像是「写漏了 `continue`」，但这就是规格：**永远只用 A 开头**，`A1` 被占就给 `A2`，字母循环实际只跑一轮。
测试里用「空集合 → A1」「有 A1 → A2」两条把这个行为钉死，防止后人「顺手修好」。

### 6. 控制字符正则「写错了也看不出来」——需要判别性用例

`CONTROL_CHARACTER_PATTERN` 在 Kotlin 源码里是 `Regex("[\\u0000-\\u0008\\u000B\\u000C\\u000E-\\u001F\\u007F]")`。
Kotlin 字符串里 `\\u0000` 会先被转义成 `\u0000` 两个字符，再交给正则引擎解释成「NUL 字符」—— **正确**。
但这条路径很容易手抖写成 4 个反斜杠（那就变成「字面量 `\u0000` 六个字符」），而**原有的用例只断言了「非控制字符不被误删」，这种 bug 完全测不出来**。

于是补了两条**判别性**用例：

- `sanitizeTimelineTagTextStripsControlCharacters`：喂真的 NUL/BEL/DEL，断言它们**消失**；同时断言 TAB（`\u0009`，在 TS 的 C0 区间**之外**）**保留**；
- `parseSanitizesControlCharactersAndTruncates` 里追加一段带真实控制字符的载荷。

写这类「正则语义」的用例时，**必须让「写错」与「写对」产生不同结果**，否则等于没测。
（本条也顺带确认了 TS 的 C0 区间确实排除了 `\t`/`\n`/`\r`。）

## 要点

- **`buildTimelineTreePromptContext` 的字符串逐字照抄**（含 8 条 AI 回复规范、`<!--WATCHWORLD_TIMELINE_DESCRIPTION_TAG:...-->` 示例、`·` 分隔符、全角冒号）。改标点会影响模型行为（`MIGRATION_CONSTRAINTS §4.3` 精神）。
- **不可见分支零泄漏**：活动分支 `visible == false` → 整段返回 `""`；父分支与其他平行分支也各自过滤。改动此函数时 `treePromptExcludesInvisibleSiblingsAndInvisibleParent` 必须继续通过。
- **`allMessages` 形参在 TS 里声明了但从未使用**。Kotlin 保留形参以对齐签名，用 `@Suppress("UNUSED_PARAMETER")` 抑制警告（零警告红线）。**不要删**。
- **`TIMELINE_COLORS` 的 Tailwind class 原样保留**（`bg-indigo-500/10 dark:bg-indigo-500/20` 等）。Compose 侧若要换算颜色，得另做映射层，**不许改这张表**。
- **`createDefaultMainTimeline(now)` 由调用方传时间**：TS 用 `Date.now()` 两次调用（`createdAt`/`updatedAt` 可能差 1ms），commonMain 没有对等物。
- **`createTimelineDescriptionTagRequest` 的 id 格式**：`timeline-description-tag-{now}-{sourceMessageId}`，`requestId` 传入优先。
- **`approve` 与 `reject` 不对称**：`approve` 看 `timelineMemoryEnabled` 且要求目标分支可见；`reject` **不看**记忆开关、也不要求分支可见（TS 源码如此）。
- **`approve` 会同步该分支下所有消息的 `descriptionTag` 缓存**（不只是改分支本身），并盖 `updatedAt`。别只改 timeline。
- **`detectTimelineIntent` 的三段判断顺序不可换**（先整串/句式切分支 → 再显式声明新建 → 最后方括号标签）。有专门的反证用例钉住「TS 不接受的写法也不能被我们接受」。
- **`ContextBuilder` 第 6 步的顺序**：内部构建的时间线树提示词排在 `extraSystemTail` **之后**（与 `api.ts:311-321` 一致，`systemSectionsFollowApiTsOrder` 仍须通过）。
