## 心得

### 1. 「库还是 v1、从未发布 → 直接改表不用迁移」是错的判据

第一版给 `worldDocuments` 加 `legacyGroup` 时判断：库还是 `version = 1`、从没发布过，
所以直接改实体、不 bump 版本、不写 Migration。**测试全绿**（`openInMemory` 每次都是新建的空库，
identity hash 自然对得上），所以我以为没事。

真实情况是用户一启动就弹窗崩溃：

```
Room cannot verify the data integrity. Looks like you've changed schema but forgot to update the version number.
Expected identity hash: ae8df70cd16a878eb40ee96b43278a2f, found: b290e3ae02d4f73042e6a286140a9b57
```

**因为开发机上 `%APPDATA%\WatchWorld\watchworld.db` 早就是 v1 结构了** —— 上一次跑
`:desktopApp:run` 时就建好了。改完实体再启动，Room 拿新结构算的 hash 与库里记的 v1 hash 不一致，直接抛。

正确的判据是 **「本机 / 用户机上有没有已存在的库文件」**，不是「这个版本发布过没有」。
而既然跑过一次应用就已经有了，这个判据在开发第一天就不再成立 ——
**结论：只要改实体，就必须 bump 版本 + 写 Migration。没有例外。**

返工内容：`version = 1 → 2`、`WwMigrations.kt` 的 `MIGRATION_1_2`、`open()` 上 `.addMigrations(...)`、
`shared/schemas/2.json`、迁移测试（`tasks/T18` 的「改动」表）。

> 这个坑的可怕处在于**它绕过了所有测试**：`openInMemory()` 每次都新建库，永远测不出「老库打不开」。
> 只有「物理文件 + 关库重开」的测试才能覆盖，所以 `StorageRoundTripTest.fileBackedDatabaseSurvivesCloseAndReopen`
> 这类用例的价值远高于它的行数。

### 2. 基线 `schemas/1.json` 会被「直接改实体」的构建污染 —— 还原它比想象中麻烦

发现崩溃后，`1.json` 已经被上次构建重写成了「含 `legacyGroup` 的 v1」——
于是 `version = 1` 与「库是 v1」两个条件同时成立、结构却不一致，这才有了那个自相矛盾的报错。
更糟的是 `identityHash` 也被改成了新结构的 hash。

还原时必须对齐**旧库文件里的真实 v1**，而不是「把 `legacyGroup` 那一行删掉就完事」：
`1.json` 的 `createSql` 有两处（`fields` 与 `createSql` 字符串），`identityHash` 也要一起还原成
旧库 `room_master_table` 里记的 `ae8df0cd…`。校验方式是拿 `sqlite3` 读旧库：

```
PRAGMA user_version;                         → 1
SELECT * FROM room_master_table;             → 42|ae8df70cd16a878eb40ee96b43278a2f
.schema worldDocuments                       → 不含 legacyGroup
```

⚠️ 用 PowerShell `Set-Content -Encoding UTF8` 写 JSON 会**加 BOM**，`WwJson.parseToJsonElement`
会报 `Unexpected JSON token at offset 2`。要写成无 BOM：
`[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`。

### 3. 没有 `room-testing` 也要能测迁移：自己按 schema 造 v1 库

`androidx.room:room-testing` 在 KMP 的 `desktopTestRuntimeClasspath` 里解析不到
（Room 2.8.5 的 `room-testing` 不带 KMP 变体，依赖直接 FAILED，而且 Gradle 报错时自己 NPE
把真实原因盖住了）。于是改成**不依赖任何新依赖**的两层验证，输入全部来自已提交的 schema JSON：

1. 结构契约：`2.json` 里 `legacyGroup` 的列名/类型/可空性，与 `MIGRATION_1_2` 的 SQL 逐字比对；
2. 端到端：按 `1.json` 造**完整** v1 库 → `WwDatabase.open` → 迁移 + 哈希校验 → 读写 → 关库重开。

造 v1 库时踩了三个坑，全在注释里留了记录：

- **`createSql` 里表名是 `${'$'}{TABLE_NAME}` 占位符**，不替换会建出一张名叫 `${TABLE_NAME}` 的表，
  报 `no such table: worldGroups`；
- **必须 17 张表全建**，少一张就报 `Migration didn't properly handle: providers(...)`；
- **索引也要建**：Room 的结构比对包含索引，少一个 `index_sessions_updatedAt` 就报
  `Migration didn't properly handle: sessions(...)`，而错误信息只列 Expected/Found 的差异片段。

### 1. 「读时迁移」遇到「导入」会静默失效 —— 老 `group` 必须在库里先活下来

这是本任务唯一一个**跑起来不报错、但功能完全没用**的坑，值得完整记下来。

Web 版的链路是：`importAllData` 把**原始 JSON 整段**塞进 localStorage（此时 `group` 还在），
之后任何组件调 `Storage.getWorldDocuments()` 时才做 `const { group: _legacy, ...rest } = d` 的迁移。

原生版没有 localStorage 这层中间态，链路变成
`parseArchive → 模型 → ConfigRepository.setWorldDocuments → SQLite → 之后读时才迁移`。
第一版我把 Mapper 写成 `legacyGroup = null`，理由是「`explicitNulls = false` 下 `null` 等于键消失，
正好对应 TS 的解构丢弃」。

**错在哪**：解构丢弃发生在**读**的时候，而 `toEntity` 是**写**的时候。
`null` 一写，`group` 就永远进不了库，`getWorldDocuments()` 那一步再也看不到它 ——
表现为「导入老存档后文档全部未分组」，而且不报任何错。

修法：`toEntity` **原样带上** `legacyGroup`；迁移后内存里的对象已经没有 `legacyGroup`
（`resolveWorldDocumentGroupIds` 返回清理过的新对象），所以再写回时该列自然清空，老 `group` 不会复活。

> **普适教训**：判断「某个字段该不该落库」的标准不是「它属不属于新模型」，
> 而是**「迁移发生在读还是写」**。迁移在读 → 原始值必须先活到读的那一刻。

### 2. 判别性用例：这条是靠「构造出 `groupId` 里躺着旧值」才测出来的

`resolveWorldDocumentGroupIds` 里最反直觉的一条是「`group` 有值但查无此名 → `groupId` 写成
`undefined`（= Kotlin `null`）」，即文档变成**未分组**，而不是「保持原样」。

如果只喂「文档本来就没分组」的样本，**「清空」与「保持原样」两种实现的输出完全一样**，测不出来。
所以用例特意构造 `doc(groupId = null, legacyGroup = "不存在的分组")` 并断言 `groupId == null`；
再配一条「`groupId` 已有值 + 也有 `group`」的样本，钉住「已有 `groupId` 优先」。

### 3. 「删除分组」踩到「`setXxx` 是全量替换」那条纪律

第一版 `deleteGroup` 用内存快照算 `remainingDocuments` 再写回。看着没问题，但内存快照可能
落后于库（例如刚导入过存档、或另一个 ViewModel 刚改过），写回就把别人的改动抹掉了。

修法：**两个列表都从库里读**（`config.worldGroups()` / `config.worldDocuments()`），
在同一个 `transaction {}` 里过滤后写回。文档特意取「读接口给的对象」而不是快照里的 ——
读接口已经跑过迁移，写回等于把迁移结果固化。

### 4. 分组树要两处环保护，不是一处

- `selfAndDescendantWorldGroupIds` 用 `guard` 防**递归栈溢出**（`TimelineMemory.depthOf` 同一手法）；
- `WorldViewModel.setGroupParent` 用 `parentId in selfAndDescendantWorldGroupIds(groups, groupId)`
  防**业务成环**。

只有前者的话，「把 A 挂到它的后代 C 下面」会**成功**，数据里就真的多了一个环，
之后 UI 的递归渲染会无限展开。用例 `settingParentToOwnDescendantIsRejected` 守住这条。

### 5. 「世界观」与「知识库」的启用语义**不对称**，不要顺手统一

| | 全局 `enabled` | 本窗口勾选 | 判定 |
|---|---|---|---|
| 知识库 | 参与（必须为真） | 参与 | `enabled && id in connectedIds` |
| 世界观 | **只在「没保存过窗口选择」时参与** | 参与 | `null` → 取全部 `enabled == true`；否则只看勾选 |

Web 版 `App.tsx` 就是这么写的（`selectConnectedKnowledge` vs `selectActiveWorldDocuments`），
两个函数都留在 T08 的 `ContextBuilder.kt` 里。T18 把世界观这一侧的语义补了用例并在
`selectSessionWorldDocuments` 的 KDoc 里写明「与知识库不对称」，避免后人「统一」成同一条规则。

### 6. 用例期望写错，比实现写错更难发现

`deleteGroupCascadesToSubtreeAndItsDocuments` 首跑失败：期望 `[旁支, 未分组]`，
实际 `[根, 旁支, 未分组]`。查下去发现**实现是对的** —— 我建了 `root`（根）与 `child`（子）两个组，
文档分别挂在 `root` 与 `grandChild` 上，删 `child` 时 `root` 的文档当然不该被删。
是我写期望时把「根文档属于 root」记成了「属于被删的子树」。

**排查手段**：没有反复重跑，而是把期望/实际各自打印出来（临时 `assertTrue(false, "DIAG ...")`），
一眼看到 `根文档 -> wg-…1000` 而 `child = wg-…2000`，立刻定位是期望错了。用完即删。



## 要点

- **只要改实体，就必须 bump `WwDatabase.version` + 写 `Migration` + 在 `open()` 里 `.addMigrations(...)`**。
  「库还是 v1、没发布过」**不是**豁免理由 —— 开发机上跑过一次 `:desktopApp:run` 就已经有 v1 库文件了。
  判据是「机器上有没有已存在的库文件」。漏了会抛
  `Room cannot verify the data integrity … Expected identity hash … found …` 弹窗崩溃（本任务实测）。
- **`openInMemory()` 测不出「老库打不开」**：它每次都是新建的空库，identity hash 天然对得上。
  改表时唯一有效的回归是「物理文件 + `WwDatabase.open` + 关库重开」。
- **`shared/schemas/` 下每个版本的 JSON 都要提交，且都不许被构建污染**：
  它们既是结构契约，也是迁移测试的输入。改完实体后如果只跑构建不还原，
  `1.json` 会被改写（`legacyGroup` 写进 v1 的 `createSql`、`identityHash` 变成新哈希），
  那时 `version = 1` 与「库是 v1」两个条件同时成立、结构却不一致，排查成本翻倍。
- **改 JSON 别用 PowerShell `Set-Content -Encoding UTF8`**：会加 BOM，`WwJson.parseToJsonElement`
  报 `Unexpected JSON token at offset 2`。用 `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))`。
- **`WorldDocument.legacyGroup` 是「读时临时字段」，不许在 UI 里读**：它的唯一合法消费者是
  `domain/WorldLibrary.resolveWorldDocumentGroupIds`。UI 只认 `groupId`。
- **`WorldDocumentEntity.legacyGroup` 必须原样落库**（`toEntity` 不许写 `null`）——
  理由见「心得 4」，这是「导入老存档后文档未分组」的唯一根因。
- **迁移位置固定在 `ConfigRepository.worldDocuments()`**（对齐 `storage.ts:361` 的 `safeGet` 之后）。
  新增任何「读世界观文档」的路径都必须走这个函数，不要直接调 DAO。
- **`selfAndDescendantWorldGroupIds` 的环保护不可删**：父级可被用户改成任意分组，
  数据里一旦有环，无 guard 的递归会 `StackOverflowError` 把界面打崩。
- **删除分组 = 连带删除**：整棵子树的分组 + 这些分组名下的文档。它**不是**「把文档移到未分组」。
- **改父级的候选必须排除「自己 + 自己的后代」**（`WorldPanel.GroupParentDialog` 与
  `setGroupParent` 各一道），否则成环。
- **`ConfigRepository.setWorldGroups` / `setWorldDocuments` 是全量替换**，会删掉不在列表里的条目；
  任何「改一条」都要 `config.transaction { 读全量 → 改 → 写全量 }`。
- **未分组文档的哨兵 id 是 `__ungrouped__`**（`UNGROUPED_WORLD_GROUP_ID`，对齐 `DocumentModal.tsx:44`）；
  模型层用 `groupId == null` 表示未分组，哨兵只在 UI 侧做分组键。
- **旧 `group` 键不进导出**：`toEntity` 落库的值在迁移后已被清成 `null`，导出里只有 `groupId`。
  `StorageRoundTripTest.legacyWorldDocumentGroupNameMigratesToGroupId` 三段一起断言。
- **世界观库目前只有「库形态」**：窗口勾选形态（`sessionDocIds` / `onToggleForSession`）还没做，
  见「遗留问题」。
- **`WorldPanel` 不要自己套滚动容器**：`FeatureDialog` 已按 `scrollable = true` 套了 `verticalScroll`，
  再套一层会让内层高度算不出来。内部用 `heightIn(max = …)` 限高。
- **`WwDatabaseMigrationTest` 不依赖 `room-testing`**（它在 KMP 的 `desktopTest` 依赖里解析不到），
  改成「按 `schemas/*.json` 自己造完整 v1 库」。造库时三个必须：**替换 `${'$'}{TABLE_NAME}` 占位符**、
  **17 张表全建**、**4 个索引也建** —— 少任何一样 Room 都报
  `Migration didn't properly handle: <table>(...)`，而报错信息只给差异片段。

## 遗留问题 / 下一步

- **⚠️ 本任务是本仓第一次真正落地 Room 迁移**：`MIGRATION_1_2` 是本仓**第一条** Migration，
  `WwDatabaseMigrationTest` 也是第一套迁移测试。下一次改表时请照抄这套模式
  （bump version → `WwMigrations.kt` 加一条 → `open()` 加 `.addMigrations` → 造 vN 库的测试）。
  ⚠️ 本仓**没有**（也不该有）`fallbackToDestructiveMigration`。
- **`WwDatabaseMigrationTest` 造 v1 库时用了硬编码的 `sessions` DDL**：`1.json` 里那条 `createSql`
  与 Room 打开库时比对的真实列对不上（`sessions` 走 `SessionConfigBlob` TypeConverter），
  所以测试里手写了一份。**将来改 `sessions` 表结构时，这两处要一起改**，
  否则迁移测试会因为「基线 DDL 与 schema 不一致」而误导。
- **窗口勾选形态未做**：Web 版 `DocumentModal` 有第二种形态（`sessionDocIds` / `onToggleForSession` /
  `onSetSessionDocs`，从输入区「本窗口世界观」进入）。本任务只做了侧边栏的**库形态**。
  接线时用 `domain/WorldLibrary.selectSessionWorldDocuments`（语义已在 T18 定死并用例守住），
  写回 `ChatSession.connectedWorldDocIds`（`null` ≠ `[]` 两态，别拍平）。
- **`SettingsViewModel` 里的 `KnowledgePanel` 仍是「平铺列表」**：知识库这一侧的分组/搜索/导入文件
  （`KnowledgeBaseModal.tsx` 有 `handleFilesUpload`）还没做。要做时新开 `KnowledgeViewModel`，
  不要往 `WorldViewModel` 里塞 —— 两者虽常一起出现，但数据源与状态完全不同。
- **分组树的拖拽移动未做**：Web 版支持把文档拖到分组上（`draggingDocId` / `dragOverGroupId`）。
  原生版用「移动」下拉替代（功能等价、少一套手势），真要拖拽时补在 `WorldPanel` 上。
- **文档正文用朴素 `OutlinedTextField`**：Web 版是 Markdown 编辑器。要不要上 Markdown 编辑形态，
  等 UI 打磨任务一起定。
- **`WorldDocument.enabled` 的界面语义容易被误解**：当前画成勾选框，但它控制的是
  「**全局**默认是否注入」，不是「本窗口启用」。窗口勾选形态落地时应把两者在视觉上分开
  （Web 版靠两个不同入口区分）。
- **`WorldPanel` 只有编译与逻辑验证，没有真窗口截图对拍**（不像 T12 有像素级验收）：
  缩进、折叠箭头、下拉弹层的观感属于未验证项。
